# Complete workflow example

This example demonstrates how to use [`rawverx`](https://github.com/ariaci/rawverx) and [`genverx`](https://github.com/ariaci/rawverx/tree/main/genverx) together with a single application version file.

The application version is embedded into the Go binary using `go:embed`, while `genverx` generates Windows `VERSIONINFO` resources from the same file. VCS metadata is obtained from the Go toolchain without linker flags or generated Go source files.

## ✨ Features

- A single `VERSION` file shared by the application and resource generator
- Runtime version information provided by `rawverx`
- Windows `VERSIONINFO` resources generated by `genverx`
- Automatic VCS metadata detection where available
- Independent Go modules for the application and generator
- No linker flags or generated Go source files required

## 📁 Project structure

```text
complete-workflow/
├── go.mod
├── main.go
├── version/
│   ├── VERSION
│   └── versioninfo.go
└── tools/
    └── genversioninfo/
        ├── go.mod
        └── main.go
```

The `version/VERSION` file contains the application version, currently `1.2.4-example`.

- [`version/versioninfo.go`](version/versioninfo.go) embeds the version and provides `version.NewInfo()` for runtime use.
- [`main.go`](main.go) retrieves and prints the resulting version information.
- [`tools/genversioninfo/main.go`](tools/genversioninfo/main.go) generates Windows resources for `386`, `amd64`, and `arm64`.

The application and generator intentionally use separate Go modules. The application depends on `rawverx`; the generator depends on `genverx`.

## 🚀 Usage

Run the following commands from the `examples/complete-workflow` directory.

### Run the application

```bash
go run .
```

The application prints the embedded semantic version together with available VCS information. The exact output depends on the Git state and the build environment.

### Generate Windows version resources

```bash
go generate ./...
```

The `//go:generate` directive in `version/versioninfo.go` invokes the generator from its own Go module. It writes architecture-specific `.syso` resources into the `version` package directory.

You can also invoke the generator directly from the example root:

```bash
go -C tools/genversioninfo run -buildvcs .
```

### Build the Windows application

For example, to build for Windows on AMD64:

```bash
GOOS=windows GOARCH=amd64 go build -o example.exe .
```

Go automatically includes the matching `.syso` resource when building the executable. The example also generates resources for Windows `386` and `arm64` targets.

> **Note:** `go generate` is not executed automatically by `go build`. Run the generator again after changing `version/VERSION` or whenever the resource metadata needs to reflect a different source state.

## 🔄 How it works

Both paths use the same `version/VERSION` file:

1. **Runtime:** `go:embed` includes the version string in the application, and `rawverx.NewInfo()` combines it with available build metadata.
2. **Windows resources:** `genverx.NewInfoWithVersionFromFile()` reads the version file, and `genverx.Generate()` produces the `.syso` files used by the Windows build.

The application can be used without Windows resources. The generator is needed only when the Windows executable should include `VERSIONINFO` metadata.

## 🧩 Module separation

The example intentionally uses two independent Go modules:

- **Application module:** Uses `rawverx` to access the embedded application version and VCS information.
- **Generator module:** Uses `genverx` to generate Windows VERSIONINFO resources before building the application.

This separation ensures that the application does not depend on the Windows resource generation libraries.

The generator has its own `go.mod` and can be executed independently using:

```bash
go -C tools/genversioninfo run -buildvcs .
```

Both modules use the same `VERSION` file but consume it differently:

- The application embeds the file using `go:embed`.
- The generator reads the file when creating Windows resources.

No generated Go source files, linker flags, or shared build-time dependencies are required.

## 🔒 Freezing Git information

Both `rawverx` and `genverx` use VCS information provided by the Go toolchain.

However, the Git information is captured at different stages of the workflow.

### Application build

When the application is compiled, the Go toolchain embeds the available VCS metadata into the executable.

`rawverx` retrieves this information at runtime using Go's build information.

The commit, dirty state, and VCS timestamp therefore describe the source state recorded during compilation, not the repository's current state when the application is executed.

### Windows resource generation

The generator obtains VCS information when its own executable is built or started through `go run`.

`genverx` incorporates the resulting version information into the generated `.syso` files.

**Once generated, these resources contain a snapshot of the version information.**

Running `go build` does not automatically regenerate them.

Consequently, modifying the repository between resource generation and application compilation can result in different Git metadata in the Windows VERSIONINFO and the application's runtime version information.

For consistent results, generate the resources immediately before building the application:

```bash
go generate ./...
GOOS=windows GOARCH=amd64 go build -o example.exe .
```

Ideally, both operations should run against the same unchanged source tree.

> **Note:** The generator and application are separate Go modules. Their VCS metadata is obtained independently, and Go's automatic VCS stamping depends on the build context. Using `-buildvcs` requests VCS stamping but does not guarantee identical metadata across independently built modules.

## 🏷️ Application versions and Git tags

The application version stored in `VERSION` and Git tags serve different purposes.

### VERSION file

The `VERSION` file defines the semantic version of the application:

```text
1.2.4-example
```

It is explicitly controlled by the application developer and represents the version reported by the application and included in its Windows VERSIONINFO resources.

Changing this file changes the application version used by subsequent builds and resource generation.

### Git tags

Git tags identify specific commits in the repository history.

For example:

```text
v1.2.4
```

A tag can mark a release, but it is not automatically interpreted as the application version by `rawverx` or `genverx`.

Neither module requires a Git tag to determine the application version.

Instead, Git metadata is used independently to identify the source revision from which a binary was built.

### Independent concepts

The two concepts are deliberately kept separate:

| Source | Purpose |
|---|---|
| `VERSION` | Defines the application version |
| Git commit | Identifies the source revision |
| Git dirty state | Indicates modifications to the working tree |
| Git VCS timestamp | Identifies the recorded commit time |
| Git tag | Optionally marks a release in repository history |

A release workflow may choose to keep the `VERSION` file and a Git tag synchronized, but this is a project policy rather than a requirement imposed by either library.

This design allows the same application version to be built from different commits while retaining information about the exact source revision used.

**The application version describes what is being released. The Git metadata identifies what was actually built.**

## 📋 Requirements

- Go 1.19 or newer for the example application
- Go 1.25 or newer to run the resource generator
- Git metadata available to the Go toolchain if VCS information is desired
